数据结构 · 四种存储方式

从内存的物理结构讲起，彻底理解顺序、链式、索引、散列存储

1 内存到底长什么样？

1.1 核心事实：每个单元 1 字节，不是 32 位或 64 位

不管你的电脑是 32 位还是 64 位，每个内存单元存储的都是 1 字节（8 位）。32 位/64 位指的是 地址总线的宽度——用多长的二进制数来给这些单元编号。

打个比方：内存就像一整排 信箱墙，每个信箱大小都一样（正好塞一张纸条 = 1 字节）。信箱上的门牌号就是用二进制编的：

  • 32 位系统：门牌号是 32 位的二进制数 → 最多编号 2³² = 4,294,967,296 个信箱 ≈ 4GB
  • 64 位系统：门牌号是 64 位的二进制数 → 理论最大 2⁶⁴ ≈ 16EB（实际没这么大，受 CPU 和主板限制）

1.2 内存单元只存值，不存自己的地址

你原来的理解——"每个内存片有一个记录值和一个地址"——需要修正：

内存单元只存值（8位二进制），地址是 CPU 通过地址总线发出去的编号，就像邮递员手上的门牌号清单，不是写在信箱上的。地址 不是 存在这个内存单元里的额外数据。

1.3 指针到底是什么？

指针就是一个 存着地址值的普通变量。它自己也是存在某个内存单元里的——只不过它存的不是"数据"，而是另一个内存单元的地址。

p 自己住在 0x2000，它里面存的是 0x1000（即 a 的地址）。这就是指针的全部奥秘。

1.4 虚拟内存：你的 APP 不会踩别人的地盘

每个进程（你的微信、浏览器、游戏）都有自己的 虚拟地址空间——你在程序里看到的地址 0x1000，跟另一个 APP 里的 0x1000，根本不是同一块物理内存。操作系统 + CPU 的 MMU（内存管理单元）负责翻译。

关键结论：你不用担心"顺序存储放在那里会不会被别的 APP 覆盖"——操作系统为每个进程划了独立的"院子"，各家的地址 0x1000 各指各的东西。数据结构的讨论都在一个进程内部进行。

你之前认为："一个内存片有两个值——记录值和地址"

实际上：内存单元只存值（8位）。地址是 CPU 通过地址总线选中的编号，就像电缆上的信号，不是存在单元里的额外字段。指针变量也只是存了一个恰好被解释为地址的数值而已。

1.5 64位CPU + 小内存，高位地址浪费了吗？

这个问题问得非常精准。答案是：没有浪费，也浪费不了——原因分两层。

第一层：今天的 64 位 CPU 并没有用满 64 根地址线。当前 x86-64 处理器虚拟地址只用了低 48 位（可以寻址 256TB），物理地址线更少（通常 40~52 根）。高 16 位（第 48~63 位）必须全部等于第 47 位的值，这叫 规范地址（canonical address）——如果出现不符合规范的值，CPU 直接报错。这么设计有两个好处：

  • 不用为目前还不存在的海量内存铺设多余的地址线，省晶体管、省功耗
  • 高位当"校验位"用，能立刻检测出非法地址

所以那个"64"更像一个 寄存器宽度（一次能处理 64 位数据），而不是说必须接满 2⁶⁴ 个内存单元。

第二层：反过来，32位CPU + 大于4GB内存条，多余的内存确实浪费了。32 位地址总线最多只能发出 2³² 个不同地址，物理上限就是 4GB。你插 8GB 内存条，操作系统只能"看到"其中 4GB（实际约 3.2~3.5GB，因为还有一部分地址空间要留给硬件映射），剩下的内存对 CPU 来说 根本不存在。这就是 32 位被淘汰的核心原因之一——内存便宜了，但地址不够用了。

一句话总结你的两个场景：64位CPU配小内存 → 高位当校验位，不浪费（且未来可扩展）；32位CPU配大内存 → 超出4GB的部分浪费，CPU物理上访问不到。

2 顺序存储（数组）

2.1 逻辑相邻 = 物理相邻

顺序存储结构就是 数组。数组的所有元素 在内存里紧挨着排成一排。没有额外的指针字段，没有索引表——就是纯数据，一块接一块。

2.2 "没有指针，程序怎么找到元素？"

答案是：首地址 + 偏移量。程序只需要记住数组第 0 个元素的地址（基地址），访问 arr[3] 时自动算出：基地址 + 3 × sizeof(int) = 0x1000 + 12 = 0x100C。

// 伪代码：程序内部自动完成的计算 arr[3] 的地址 = arr的基地址 + 3 × sizeof(元素类型) = 0x1000 + 3 × 4 = 0x100C // 不需要额外的指针，因为顺序存储的"规律"就是相邻 // 这正是顺序存储的优势：寻址极快，O(1)

2.3 优劣势

描述
✅ 读取 O(1)给定下标，瞬间算出地址
✅ 省空间不浪费任何字节在指针上
❌ 插入/删除 O(n)中间插入一个元素，后面全部要向后挪
❌ 需要连续空间要存100万个元素，得找一块 100万×4字节 的连续空地

你之前认为："顺序存储没有指针和关键字，程序无法识别，可能只适合系统程序"

实际上：顺序存储（数组）是 所有程序 最常用的数据结构，没有之一。Python 的 list、JavaScript 的 Array、Java 的 ArrayList，底层全是顺序存储。程序不需要"关键字"来识别——编译器/解释器在生成机器码时已经算好了每个元素的偏移量。至于"被别的 APP 占用"，1.4 节的虚拟内存机制完全解决了这个问题。

一排连续的停车位。你知道 1 号车位在哪，要知道 5 号车位在哪，往前走 4 个车位就到了——不需要在每个车位上贴箭头。这是最朴素也最高效的存储方式。

3 链式存储（链表）

3.1 核心真相：指针就在数据元素里面

这是你之前最纠结的问题——"指针从哪来？"答案是：指针就是数据元素的一个字段，和数据打包在同一个结构里。计算机不需要"自动识别"它是链式存储——是你写的代码在遍历时自己顺着指针跳的。

// 伪代码：链表的节点结构 结构体 Node { data: 整数 ← 数据字段（你想存什么存什么） next: 指向Node的指针 ← 指针字段（存下一个节点的地址） } // 遍历链表的逻辑 current = head // 从头节点开始 当 current ≠ null 时: 输出 current.data // 访问当前节点的数据 current = current.next // 顺着指针跳到下一个节点

3.2 内存布局：节点散落四处，指针串联

3.3 你的两种"可能性"哪个对？

你问的 "可能性2" 完全正确：指针是数据元素内部的一个数据项，就像结构体的一个字段。计算机不需要"知道"这是链式存储——是你写的 current = current.next 这行代码在告诉计算机："去读 next 字段里的地址，跳到那里继续。"

3.4 优劣势

描述
✅ 插入/删除 O(1)改两个指针就好，不用搬数据
✅ 动态扩容随时 new 一个节点，不用提前预留大块连续空间
❌ 查找 O(n)必须从头一个一个跳着找
❌ 额外空间每个节点都要多存一个指针（4 或 8 字节）

寻宝游戏（scavenger hunt）。每个宝箱里有一张纸条写着下一个宝箱的位置。宝箱们散布在城市各个角落（物理不连续），但你能顺着纸条一个个找到（逻辑连续）。"纸条"就是指针，它是宝箱内容的一部分，不是宝箱自带的神秘第三属性。

4 索引存储

4.1 数据和索引分开存

索引存储 = 数据部分随机放 + 单独建一个 索引表（也是一个数组，存在内存里）。索引表里每行记着：关键字 → 该数据在内存中的地址。

4.2 查找流程

// 伪代码：通过索引找"张三" 步骤1: 在索引表里二分查找 key="张三" → 找到条目: key="张三", addr=0x3000 步骤2: 直接跳到地址 0x3000 → 读取张三的完整数据 // 索引表本身是按键排序的顺序存储（数组），所以查找索引表很快 // 找到索引条目后，跳转到数据区的过程是 O(1)

4.3 索引表也存在内存里

你问"索引表存在哪里"——就在内存里。它本质上也是一个顺序存储的数组（或树），占的内存大小取决于索引项的数量和每条索引项的大小（关键字 + 地址指针）。数据库的 B+ 树索引就是这个思路的工程实现。

图书馆的检索卡片柜。书（数据）按到馆先后顺序随意放在书架上，但你可以在卡片柜（索引表）里按书名首字母快速找到卡片，卡片上写着那本书在第几排第几层。卡片柜本身也是一件家具，放在图书馆里——跟书用的是同一栋楼的面积。

5 散列存储（哈希表）

5.1 用函数算出地址

散列存储不是"把数据放在哪"的问题——是 先算出来放哪，再放过去。给定关键字 key，用一个哈希函数 H(key) 算出存储地址，然后直接放到那个位置。查找时再做一遍 H(key) 就知道它在哪了。

// 伪代码：哈希存储与查找 存储(key, value): addr = H(key) // 哈希函数算出地址，例如 H("张三") → 3 table[addr] = value // 直接放到算出来的位置 查找(key): addr = H(key) // 同样的哈希函数再算一遍 返回 table[addr] // 直接从那个位置取出来

5.4 优劣势

描述
✅ 查找 O(1)理想情况下，算一次哈希函数就知道在哪
✅ 插入 O(1)同样算一次，直接放过去
❌ 冲突退化冲突多了退化成 O(n)，需要好的哈希函数 + 扩容策略
⚠️ 无序无法按顺序遍历

你之前担心："两个 APP 通过哈希算出来的地址会不会一样，互相覆盖？"

实际上：不会。虚拟地址空间隔离保证了不同进程的"地址 0x3000"指向不同的物理内存。哈希冲突只在 同一个哈希表内部 发生——张三和李四的 key 算出了同一个槽位——用开链法或开放定址法处理即可。

酒店前台分房间。客人说"我叫张三"，前台用一个公式（比如名字笔画数 mod 房间总数）算出房间号，直接给你房卡。但如果王五算出来也是同一间——冲突了！前台要么让王五去隔壁空房间（开放定址法），要么在那间房里加一张折叠床（开链法）。不管怎样，隔壁酒店（另一个 APP）的客人不会跑到你这来。
