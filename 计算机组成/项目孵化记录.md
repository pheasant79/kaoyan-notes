## 2. 当前核心困扰

### 2.1 教材是抽象模型

408 中的计算机组成内容，本质上是对真实计算机系统的抽象。教材为了讲清基本原理，会压缩、简化或理想化很多实现细节。

这会造成一个问题：学习者容易把“教材模型”误认为“现实机器的完整工作方式”，或者在教材模型与现代计算机之间来回切换时失去参照系。

### 2.2 教材带有较强的传统计算机色彩

教材中经常使用较老、较经典的计算机结构和部件描述。这些描述对于考试建模有用，但与今天接触到的 CPU、缓存、内存、总线、操作系统和编译器实现并不完全一致。

因此需要在学习过程中持续区分：

- **考试模型**：为了考察原理而采用的简化结构。
- **经典实现**：教材概念在传统计算机中的典型落地方式。
- **现代实现**：当代处理器和存储系统中更常见的实现。
- **不可混用之处**：哪些结论只在特定模型或假设下成立。

### 2.3 现有资料逐渐增多，但尚未形成统一系统

这些内容可以作为后续整理时的已有素材，但暂不假设它们的章节归属、术语口径和图示风格已经统一。

## 5. 内容整理原则（暂定）

### 5.1 先保留问题，再给结论

不能只留下最后的标准答案。原始困惑和错误路径本身也是复习材料，因为它们揭示了概念最容易混淆的地方。

### 5.2 明确模型边界

讲解一个结论时，尽量说明它依赖的前提，例如：

- 是否假设单总线或多总线结构。
- 是否假设按字寻址或按字节寻址。
- 是否假设指令定长。
- 是否讨论主存、Cache、TLB 或虚拟存储器中的哪一层。
- 是否只针对 408 题目中的抽象数据通路。

### 5.3 术语要稳定，必要时允许双重命名

同一概念如果在教材、不同课程或现代资料中有不同叫法，应记录主名称、别名和使用场景，避免把名词差异误认为机制差异。

### 5.4 图示优先服务于推理

图不是装饰。每张图都应回答一个具体问题，例如：

- 数据从哪里来、经过什么部件、到哪里去。
- 地址的哪几位被哪一级译码器使用。
- 某个时钟周期内哪些控制信号有效。
- 连续编址与交叉编址为什么会产生不同的访问行为。

当前新增约束：

- 每个重要知识点优先产出一张“主图”或“关系图”，而不是先写长篇文字。
- 文字只承担图例、边界条件、读图提示、术语解释和错误纠正。
- 图应有稳定编号和名称，便于后续章节引用与修改。
- 图的修改必须留下变更记录，不能只替换成“看起来更新”的最终版本。

### 5.5 图谱的跨章节修改规则

当后续章节发现需要修改、补充或拆分上一章的图时，新增记录至少包含：

```md
## 图谱变更记录

- 修改图：G-xxx 图名
- 来源章节：第 x 章 / 第 x 节
- 修改位置：节点、连线、标签、层级或注释
- 原内容：
- 新内容：
- 修改原因：
- 是否影响其他图：是 / 否
- 需要回查的关联图：
```

这样既能保留学习过程，也能防止后续为了适应新章节而无声改变旧结论。

### 5.5 允许版本化修订

后续如果新的理解推翻旧记录，不直接删除旧内容，而是保留“原结论—发现问题—修订结论”的过程，并注明修订原因。

## 10. 新增工作流：先图谱审查，后 HTML 施工

### 10.1 两阶段门槛

以后用户提供一章或一段新知识时，**第一轮只做图谱审查，不直接修改 HTML**。必须先输出一份简短但具体的“施工前分析”，由用户确认后才能进入第二轮。

#### 阶段 A：施工前分析（不改 HTML）

分析至少包含：

1. 本次内容涉及的章节、概念层级和与旧图的关联。
2. 建议新增、修改、拆分或删除的图，按稳定图号列出。
3. 每张候选图要回答的唯一核心问题。
4. 图形类型：结构剖面、关系图、数据通路、时序叠层、地址映射、位字段、存储阵列、同骨架对照等。
5. 哪些内容**不需要画图**，改用短说明、部件注释、对照表、公式或边界提示即可。
6. 每张图需要放进图内的最少文字，以及图外需要补充的部件说明。
7. 对旧图的影响：引用图号、修改位置、修改理由、是否会改变原结论。
8. 未确定的教材口径、实现前提或需要用户确认的范围。
9. 预计施工顺序和验收重点：结构语义、文字可读性、缩放、交互、离线打开。

阶段 A 的结尾必须明确写出：**“等待确认，暂不修改 HTML。”**

#### 阶段 B：HTML 施工（用户确认后）

只按已确认范围修改 HTML，并且：

- 优先修改已有母图和局部图，不无故新建重复图。
- 每张图保留稳定 ID、名称、版本和修改记录。
- 图内文字、图外解释和模型边界分别放置，不把页面变成长篇讲义。
- 完成后做离线打开、桌面、窄屏、交互和语义检查。

### 10.2 何时需要图，何时不要图

#### 优先画图

- 部件的空间包含关系、接口和连接关系。
- 数据、地址或控制信号经过哪些部件。
- 取指、读、写、I/O 等动作在同一结构上的临时路径。
- 虚拟地址→物理地址→内存控制器→DRAM 的层次映射。
- 高位/低位字段、字节/字、芯片位宽、存储阵列、行列译码。
- 不同模型使用同一骨架时“哪里变了”。
- 连续编址、交叉编址、Cache 层次等需要比较空间或时序的知识。

#### 通常不单独画图

- 一个部件的一句话定义。
- 单个术语的别名、缩写、单位或记忆提示。
- 没有结构关系的简单优缺点列表。
- 只需给出一个公式、边界条件或易错点的内容。
- 同一张图已经能直接表达、再画只会重复的文字。

这些内容应作为图旁的短注释、部件说明、对照表、公式或折叠说明，而不是为了“有图”强行画流程图。

### 10.3 图文比例与部件说明

“以图为主”不等于“图中只放名词”。凡是图中出现的关键部件，都应有一句短说明，优先放在图旁的注释栏或图例中。例如：

| 部件 | 最小说明示例 |
|---|---|
| ACC | 累加器：保存累加结果或一个中间操作数 |
| MQ | 经典乘商寄存器：乘除法中保存乘数、商或中间结果，具体看模型 |
| X | 教材抽象中的操作数临时存储寄存器 |
| ALU | 执行算术和逻辑运算 |
| CU | 译码、产生时序和控制信号 |
| PC | 保存下一条指令地址 |
| IR | 保存当前指令或指令操作码，取决于模型 |
| MAR | 保存本次存储访问的地址 |
| MDR | 保存读出或待写入的数据/指令字，不保存地址 |

规则是：图内保留短标签，图外补齐最小有效解释；不追求字越多越好，但不能只留下无法复习的缩写。

## 11. HTML 图示实现规范（必须精确执行）

### 11.1 图的技术形态

当前高质量图谱的实现方式是：**HTML + CSS + 内联 SVG + 少量原生 JavaScript**。

- 不是用 PNG 生成图作为知识源。
- SVG 使用 `viewBox` 定义坐标，图形由 `<rect>`、`<path>`、`<line>`、`<text>`、`<g>` 等矢量元素组成。
- CSS 统一颜色、边界、线宽、字体和响应式布局。
- JavaScript 只负责模型/路径切换、部件高亮、定位和缩放，不负责生成图形。
- 禁止 Mermaid、Canvas、CDN、外部字体和必须联网的脚本。
- PNG 只能用于截图验收、对比或导出预览，不能代替 SVG 源图。

### 11.2 SVG 组织

每张图必须有稳定的结构 ID，例如：

```html
<section id="g1-01">
  <svg id="fig-g1-01" viewBox="0 0 1600 900">
    <g id="g1-01-cpu" data-part="cpu"></g>
    <g id="g1-01-main-memory" data-part="memory"></g>
    <g id="g1-01-bus-address" data-path="address"></g>
    <g id="g1-01-bus-data" data-path="data"></g>
    <g id="g1-01-bus-control" data-path="control"></g>
  </svg>
</section>
```

每张图要有 `<title>`、`<desc>` 或等价的短说明；局部图要能从母图跳转或定位。结构关系、数据路径、控制路径、局部放大引线必须用不同的 SVG 语义，不能让一条箭头同时表示多个意思。

### 11.3 默认缩放与版式

这是当前 v0.2 的待修订问题，v0.3 必须落实：

- 常态下每张图默认“适配容器宽度”，不能要求用户拖页面底部或横向进度条才能看完整图。
- SVG 默认 `width: 100%; height: auto; min-width: 0`；需要放大时在图谱控制栏提供缩小、适配宽度、100%、放大等控制。
- 放大后的横向滚动只能发生在该图自己的画布内，不能把整页撑出水平滚动。
- 移动端默认仍显示完整结构；文字可缩小但不得裁切、重叠或跑出父容器。
- 三联对照图必须在各自卡片内适配宽度，不能因为统一的最小宽度把三幅图截断。
- 图标题、图号、读图顺序和关键说明应保持在图附近，不让用户在页面上来回寻找。

### 11.4 质量验收门槛

HTML 交付前至少检查：

1. 图是否表达空间结构而不是把所有内容画成流程框。
2. 地址、数据、控制线是否方向和颜色一致；结构模式不显示误导性的大箭头。
3. 关键部件是否有最小解释，尤其是 ACC、MQ、X、ALU、CU、PC、IR、MAR、MDR。
4. 默认视图是否能完整看到每张图；缩放后是否只在局部画布内滚动。
5. 桌面、窄屏和移动端是否无裁切、遮挡、重叠或异常横向页面滚动。
6. 双击本地 HTML 是否可打开，控制台是否无错误，是否无外部资源请求。
7. 后续章节能否通过稳定图号修改旧图，而不是复制出相互矛盾的新图。

## 12. 质量优先下的 token 优化

目标不是单纯减少字数，而是**不压缩关键判断，只压缩重复劳动**。

### 应该做的优化

- 先读取项目 Markdown 的当前规则、图号和待确认事项，再读取与本次问题直接相关的 HTML 区段；不重复加载无关章节。
- 将用户输入先归并为“事实、理解、疑惑、修正、图示需求”五类，避免同一事实在分析、HTML 和日志中重复展开。
- 阶段 A 只输出候选图清单、每图目的、图形类型、文字范围和风险；不提前生成完整 HTML 代码。
- 用户确认后只对批准的图做增量修改，优先 `apply_patch` 修改局部 SVG/CSS/JS，不重写整页。
- 共享颜色、线型、箭头、字体和交互逻辑；新图复用现有 SVG 组件，不重新发明一套样式。
- 只在高风险改动后做完整浏览器回归；纯文字或单标签修订做局部检查即可。
- 每轮把已经确定的模型边界和术语口径写回 Markdown，避免下一轮重复争论。

### 不应该做的优化

- 不能为了省 token 跳过施工前分析、图号规划或语义验收。
- 不能把关键部件说明删成只剩缩写。
- 不能把多个不同问题硬塞进一张图来省图数。
- 不能因为已有旧图就不检查其空间语义和缩放表现。
- 不能在未确认范围前生成大段 HTML，再因为范围变化整体返工。

### 推荐的每轮输出长度

- 施工前分析：短而完整，优先表格和条目，通常控制在 500～1000 字以内；复杂章节可超过，但不得省略风险和待确认项。
- HTML 施工说明：只报告修改了哪些图、哪些部件、哪些交互和验证结果，不重复粘贴整页代码。
- Markdown 记录：只追加新规则、变更原因和稳定结论，不复制整份旧文档。

## 13. PNG、SVG 与视觉检查的边界

### 13.1 当前图是怎么做的

当前第一章的图不是 PNG，也不是 ImageGen 生成的图片。实现链路是：

```text
图谱规格确认
    → 手工组织 HTML 内联 SVG
    → CSS 定义颜色、线型、布局和响应式规则
    → 原生 JavaScript 控制模型、路径、高亮和缩放
    → 浏览器渲染截图
    → 视觉检查并修正 SVG/CSS
```

SVG 中的矩形、路径、文字、分组和稳定 ID 都是可编辑的结构。这样后续章节可以精确修改某一条总线、某个部件或某个局部图，而不是重新生成一张不可追踪的位图。

### 13.2 PNG 的使用边界

- PNG 适合截图验收、导出预览、照片、纹理或装饰性插图。
- PNG 不作为计算机组成主图的知识源，因为文字难以精确修改，连线没有语义 ID，缩放会损失清晰度，也无法方便地做局部高亮和交互。
- 如果未来需要历史机器照片或芯片实物照片，可以把 PNG 作为 SVG 结构图旁的辅助材料，而不是替代结构图。

### 13.3 是否需要视觉能力

- **生成核心结构不依赖图像生成能力**：只要能准确规划坐标、边界、连线和标签，就可以用 SVG 完成。
- **高质量交付需要视觉检查**：浏览器截图能发现纯代码检查不容易发现的问题，例如文字压线、箭头过大、局部图被裁掉、三联图被最小宽度截断、移动端出现整页横向滚动等。
- 结构图、版式、缩放、响应式改动应做视觉检查；只改一条定义或 Markdown 记录时不必重复完整截图。

### 13.4 token 成本与控制办法

内联 SVG 比一段 Markdown 更耗 token，因为每个部件都要有坐标、样式和文字；但它换来了可编辑、可缩放、可交互和可追踪。当前第一章成本偏高，主要原因是首次建立母图并经历了多轮渲染修正，而不是因为需要生成 PNG。

以后降低成本的顺序是：

1. 先确认图谱规格，避免生成后整体推倒。
2. 复用已确认的 SVG 组件、颜色、箭头、图例、缩放和交互代码。
3. 只修改受影响的 `<g>`、CSS 规则或局部说明，不重写整个 HTML。
4. 图内保留短标签，部件解释放到紧凑说明栏，避免把大量文字硬编码进 SVG。
5. 只有结构或版式发生变化时才做完整视觉回归；纯文字修订做局部检查。

结论：**SVG 负责准确表达和长期维护，视觉检查负责发现渲染问题，PNG 只负责预览或辅助素材。**
